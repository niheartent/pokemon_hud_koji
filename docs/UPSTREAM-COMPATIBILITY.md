# 弦九核心适配与后续检查

## 当前适配

两套正式导入包以及黑白独立版内置 v4.0.45。核心源码仅维护一份：`src/shared/upstream/pkm-hud.js`；`manifest.json` 固定上游 Git 提交、版本与 SHA-256。构建验证哈希，避免原版同版本号静默修改导致产物无法复现。旧 JSON 保留历史元信息与旧版回归参考，已不作为当前业务核心来源。

之前的失败来自对原版样式注入位置的依赖。剑盾 v1.6.0／黑白 v0.4.0 进一步取消了这一依赖：共享 `presentation-boundary.js` 在合成时排除原版 CSS 构建与注入，安装自有样式；`presentation.js` 提供 111 个固定组件函数及根布局。下载的新核心中的同名模板不会用于生成最终界面，缺失的模板由本地包补齐。

模板是从已接受的 v3.3.29 一次迁入并由本仓库维护的代码，不会随核心下载重新提取；剑盾装饰器现在只组合本地模板。`presentation-contract.json` 记录组件需要的 54 个服务函数、关键状态以及固定属性色表；缺失功能接口会拒绝合成。

核心的图源映射、Mega 形态候选、等级滑块调度和数据诊断保留。真实浏览器验证主页、详情及八个页面；额外模拟删除全部上游组件和 CSS，验证仍能启动、打开这些页面且实际样式完全一致。完整业务和配色回归另外运行。

本次剑盾 v1.6.1／黑白 v0.4.1 适配上游删除 pkImgFix：它是旧图源修复辅助函数，已不作为必要业务接口；仅在旧核心提供时调用，新核心交给 resolvePkmImgs 和 hudResolvePkidbImages。设置接入可选数据源切换；旧核心没有该功能时不显示。已验证历史发布版在线安装与刷新启动。

## 如何检查下一版

1. `npm run build` 构建当前固定核心。
2. `npm run check:upstream` 获取上游当前文件对应提交，在内存中执行语法和接口合成检查。候选源码与报告仅写入忽略的 `artifacts/`。
3. PowerShell 设置 `$env:UPSTREAM_CANDIDATE='artifacts/upstream-candidate.js'` 后运行 `node tests/upstream-compatibility.cjs`，再运行 `node tests/upgrade-from-published.cjs`，结束后 `Remove-Item Env:UPSTREAM_CANDIDATE`。第二项验证旧发布版检查、真实 IndexedDB 安装、刷新启动；候选版本高于固定核心时，也测试当前发布版只升级核心。全部在模拟宿主中执行，不操作真实聊天。
4. GitHub Actions 的 **Check latest Xianjiu core** 可手动运行同一检查，下载报告。它没有推送或发布权限。
5. 确认上游差异与浏览器检查后，更新共用快照及 manifest，增加美化版本，运行 `npm run build`、`npm test`、`npm run package`、`npm run verify`，再发布新标签。

## 可兼容与需要人工适配的边界

- 上游页面模板、样式颜色和原版 CSS 注入位置变化：不会进入我们的展示层；甚至可以没有原版模板和 CSS。
- 核心新增图源、形态映射、业务字段：保留业务；新增字段要由我们明确接入模板，不自动继承上游 HTML。
- 更新器检查和安装分离、版本与数据库身份、唯一注入点：明确校验，失败时不安装未知合成包。
- 关键功能函数改名、作用域搬迁、MVU 数据模型／宿主 API 改动、交互绑定改变：必须更新功能适配和运行测试，不能承诺自动兼容。
- 黑白双屏布局仍适配核心 render／openPage 的挂载与生命周期；剑盾同样使用核心交互绑定。这里仍是源码作用域中的函数契约，不是弦九官方提供的独立 SDK。
- 固定基础、布局和主题由本仓库维护。上游 CSS 不参与最终样式；原版调色缓存不参与剑盾主题。

## 发布原则

核心与 UI 版本分别管理；同一版本文件不覆盖。GitHub 检查成功只表明覆盖到的接口和模拟场景通过，不会自动发布。新增业务场景需加专门验证，不能用单纯语法通过代替运行验证。

## 遇到类似问题如何适配

| 上游变化／现象 | 检查与处理 | 是否要发布新美化版 |
| --- | --- | --- |
| 只修复业务内部实现，函数、字段与事件契约相同 | 合成、页面运行、旧版安装刷新都通过后，可用现有更新器接入 | 通常不需要 |
| 删除旧辅助函数，例如 pkImgFix | 搜索本地所有调用，确认功能是否已由现有解析器承担；删除必要接口要求，只在旧核心提供时调用 | 需要；只放宽检查而保留调用会运行报错 |
| 关键函数改名／参数或返回值改变 | 核对行为后在适配层明确映射；同步服务契约及调用者，验证真实受影响交互 | 需要；禁止给存储、装备或安装接口加空实现 |
| 新增设置、字段或按钮 | 业务核心保留；在自有模板明确加入控件与 data-*，核对核心绑定；旧核心没有能力时隐藏选项 | 要显示新功能就需要 |
| 修改原版 CSS／HTML | 自有展示模块继续使用本地模板与样式；核对交互选择器、事件绑定和生命周期是否也变动 | 纯样式变化通常不需要 |
| 图源地址迁移 | 对比业务解析器和自有模板中写死的 URL；检查资源真实下载、失败回退及镜像 | 自有模板受影响时需要 |
| render／openPage 或挂载作用域改变 | 调整双屏、弹窗或根布局适配；验证切页、滚动、关闭和重复刷新 | 需要 |
| 下载失败／SHA-256 不符 | 先区分网络、缓存与发布产物问题；核对清单、标签文件、Release 附件和 Git 中的字节 | 包或更新器有问题才发新版 |

### 具体操作顺序

1. 保存完整诊断文字：核心版本、美化版本、错误函数名、平台、触发操作、控制台堆栈。截图可辅助，不能代替报错文字；分享前去除令牌和私人聊天数据。
2. 获取最新候选并与固定快照比较：`git diff --no-index src/shared/upstream/pkm-hud.js artifacts/upstream-candidate.js`。退出码 1 表示有差异。
3. 在自有源码中查找报错符号，覆盖剑盾与黑白两个调用方，避开生成目录及历史 versions。例：`rg -n 'pkImgFix' src/shared src/swsh src/bw2 --glob '*.js' --glob '*.cjs' --glob '!宝可梦*' --glob '!upstream-update-fixture.js' --glob '!pkm-hud.js'`。
4. 先确认旧函数的职责和新实现，再决定是否可选。只有已被其他接口承担的辅助行为适合 `typeof` 检查；不可借此跳过必要的数据写入、权限或校验步骤。
5. 必要接口在 `presentation-contract.json` 与各通道 composer 中检查；自有控件改 `presentation.js`，布局和生命周期改各通道 adapter。服务存在并不保证参数、返回值或事件行为兼容。
6. 对照本次差异验证受影响路径。候选运行测试覆盖启动与页面；升级测试覆盖下载合成、安装和刷新。图源网络、安卓渲染、真实宿主写回仍需对应环境验证。
7. 需要新适配器时，固定核心提交和哈希，增加受影响通道的 UI 版本，再构建、回归、打包和校验。共享展示层修改时同时发布两套。不要覆盖已发布版本目录。
8. 推送源码、清单及新标签；等待发布任务完成，确认远程清单与标签脚本版本一致，脚本 SHA-256 和附件 digest 匹配。本仓库黑白构建统一文本换行，避免 Windows 与 Linux 产物不同。

### 更新器的实际边界

更新器会同时检查美化清单和弦九核心；有新美化版时先取其已校验适配器，再合成最新核心。因此修复旧适配器后，新 UI 包可以让旧安装继续升级。

若最新核心不兼容，只有存在更新的美化发布包，且其中核心不低于当前已安装核心，才会采用已验证发布组合；否则停止安装并报告原因。不能保证任意未来核心自动兼容，也不会自动降低核心版本。

同一个核心版本号的源码或哈希变化，应人工检查。当前客户端主要按版本号判断更新；上游不增加版本号时不会自动视为核心更新。确需分发修正内容时可提高 UI 发布版本，以经过验证的发布包交付。
